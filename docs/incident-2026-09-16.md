# Incident of 2026-09-16 — the world that "reset"

## Summary

A dedicated server (without `-savedir`) and the local game used the same save folder. After a
4-hour session in the game, the server was started and closed; the newest save was left without
its `.db2`. When the world was opened again, Valheim generated a new world from the same seed,
saved over it and, on the next loads, deleted the real world's chunks as "orphans".

The world was recovered to its 01:49 state by rebuilding the `_main.N.chunks` index from chunks
that survived in a copy made in time. The building done in the following 2h19 was lost.

## Causes

1. **Shared folder.** Without `-savedir`, the server writes to `LocalLow\IronGate\Valheim`, the
   game's own folder.
2. **Closed without saving.** There was no `-logFile`, so the exact mechanism cannot be proven,
   but the `.db2` disappeared within the window in which the server ran and was closed.
3. **Silent regeneration.** Valheim does not ask: if the newest save lacks its `.db2`, it creates
   another world and then cleans up the old files.
4. **No backup outside the folder.** The game's automatic backups live inside `worlds_local` and
   went with it.

## What changed (and where it lives in the code)

| Protection | Where |
|---|---|
| `-savedir` mandatory; the game's folder refused | `ProfileValidator`, `LaunchArguments` |
| `-logFile` always, log archived at every start | `LaunchArguments`, `LogArchiver` |
| Server without a window; stopped only by Ctrl+C with the save confirmed | `HiddenConsoleLauncher`, `ConsoleSignal`, `ServerController.StopAsync` |
| The newest save must be complete, with all its chunks | `WorldInspector` |
| Emergency stop on `missing _main.N.db2` (N > 0) | `ServerController.EmergencyKill` |
| Verified backup before starting and after stopping | `BackupService`, `ServerController` |
| Restoring never deletes or mixes files | `BackupService.RestoreAsync` |
| Creative mode that turns off for real, checked in the `.fwl2` | `LaunchArguments` (`-preset` always), `ServerController.OnSaveCompleted` |
| One server per world/port; servers started elsewhere are detected | `WmiServerProcessLocator`, `ServerManager` |
| Chunk index rebuild | `ChunkIndexRebuilder`, `vsm rebuild-index` |
| Shutting Windows down saves the worlds first | `TrayIcon` (`WM_ENDSESSION`), `MainWindow.SaveServersBeforeWindowsEnds` |
| The game's folder is recognised through junctions, symbolic links, `subst` drives and 8.3 names | `ValheimPaths.SameDirectory` (`FinalPath`) |
| A save folder in OneDrive/Dropbox/Google Drive needs confirmation; the default leaves Documents when it is synced | `ProfileValidator`, `ValheimPaths.CloudSyncProvider`, `DefaultServersRoot` |
| Saves and backups never inside the program folder (replaced on update) | `ProfileValidator` |
| Copying a game world warns when the game is open and explains that the copies stay separate | `NewServerViewModel` |
| Installer: does not replace files while the app is open, does not use Restart Manager (which would stop the servers), installs only into an empty folder or a previous install, refuses to uninstall while a server runs and never touches worlds, backups or settings | `build/installer.iss` |

## Late consequence: the world started to duplicate itself

During the recovery, the real chunks were paired with the regenerated world's `.db2`. That `.db2`
marked only 52 zones as generated, but the chunks had objects in 284. Every time someone came near
one of the 232 unmarked zones, the game generated it again on top: vegetation, ore, mushrooms,
crypt entrances, treasure chests and a second spawn controller.

On the night of 09-16 the players noticed mushrooms that "came back", copper that broke twice and
too many enemies. Analysis of save 69 found 16,186 copies among 57,019 objects, 141 zones with
double spawns and 91 zones still to be duplicated. The new protection:

| Protection | Where |
|---|---|
| Full read of the objects and of the zone list | `ChunkObjects`, `WorldDatabase` |
| Detection of copies, double spawns and unmarked zones; warning before starting | `WorldRepair.Scan`, `ServerController.Preflight` |
| Repair with a backup first, a new save and a check (player-built pieces are never touched) | `WorldRepair.Repair`, `ServerController.RepairWorldAsync`, Dashboard, `vsm repair-world` |

## Found during development

A server launched from a process that "ignores Ctrl+C" (terminals, schedulers, IDEs that use new
process groups) inherits that flag and **never** saves when it receives Ctrl+C. The manager clears
the flag before launching (`SetConsoleCtrlHandler(NULL, FALSE)`).
